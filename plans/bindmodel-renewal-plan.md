# BindModel 웹사이트 리뉴얼 계획서

- 작성일: 2026-10-22
- 대상 저장소: `white-base/white-lab-bind-model`
- 문서 상태: HTML 구현 기준으로 갱신 (2026-10-22)
- 목표: 최신 문서를 기반으로 `docs/` 중심의 공식 문서 사이트를 만들고 GitHub Pages로 운영한다.

## 1. 추진 방향

방문자가 BindModel을 이해하고, 설치한 뒤, 첫 데이터 바인딩을 실행하고, 필요한 API를 찾아볼 수 있는 개발자 문서 사이트를 구축한다. 메인 화면은 이 학습 경로로 안내하는 입구로 구성한다.

콘텐츠는 첨부된 `10.문서.zip`을 기준으로 갱신한다. 기존 `www.bindmodel.com`은 상단 메뉴, 문서 사이드바, 본문 목차 등 정보 구조를 참고한다. 기존 사이트의 버전 번호, 코드, 기능 설명, 성능 수치는 최신 정보로 간주하지 않는다.

사용자의 후속 요청에 따라 순수 HTML·CSS·JavaScript 방식으로 구현했다. `docs/` 안의 파일을 그대로 게시할 수 있다. 실제 저장소 push, Pages 활성화, 도메인 변경은 수행하지 않았다. 구현·검수 결과는 `plans/content-migration.md`와 `README.md`에 기록한다.

## 2. 확인한 현재 상태

### 계획 수립 당시 저장소

- 로컬 저장소에는 `README.md`만 있으며, `docs/`, 사이트 설정, 배포 워크플로는 아직 없다.
- 현재 브랜치는 `main`, 원격 저장소는 `git@github.com:white-base/white-lab-bind-model.git`이다.
- GitHub의 Pages 활성화 여부, 저장소 공개 범위, Actions 권한, 도메인 설정은 아직 확인하지 않았다.

### 기존 사이트

`www` 주소는 이번 조사 도구로 열리지 않았지만, [bindmodel.com](https://bindmodel.com/)과 [한국어 문서](https://bindmodel.com/ko/docs/quick-start/)에서 구조를 확인했다.

| --- | --- | --- |
| 상단 메뉴 | 빠른 가이드, 예제, Posts, API | 문서와 예제 중심으로 정리 |
| 문서 탐색 | 시작하기, 기본 기능, 고급 기능, 레퍼런스 | 첨부 문서의 최신 분류로 재구성 |

## 3. 1차 구축 범위

### 포함

- BindModel 소개와 빠른 시작으로 연결되는 메인 화면
- 시작하기 3개, 기능 설명 7개, 고급 기능 6개, API 6개, CRUD 튜토리얼 1개 이전
- 첨부 이미지 5개의 경로 정리와 대체 텍스트 작성
- 한국어 UI, 전체 문서 검색, 사이드바, 본문 목차, 이전·다음 페이지
- 코드 구문 강조·복사, 표, 안내 박스, Mermaid 다이어그램
- 모바일 대응, 밝은·어두운 테마, 키보드 탐색
- 페이지 제목·설명, 공유 메타데이터, 사이트맵, 404 안내
- GitHub Actions 빌드와 GitHub Pages 배포 구성

### 후속 확장

- 영어 문서 번역 및 언어별 URL
- React·Vue의 실행 가능한 연동 예제
- 브라우저에서 직접 조작하는 CRUD 데모
- 릴리스별 문서, 변경 이력, 블로그·Posts
- 첨부에 없는 클래스의 신규 레퍼런스

GitHub Pages는 정적 사이트 호스팅이므로 실제 데이터 저장과 서버 API는 별도 시스템이 필요하다. 1차 CRUD 문서는 코드와 화면으로 설명하고, 실행 검증에는 로컬 mock 응답을 사용한다. 브라우저 체험판을 추가한다면 메모리 또는 브라우저 저장소를 사용하는 방식으로 별도 설계한다. [GitHub Pages 설명](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## 4. 확정 기술 구성

**정적 HTML + CSS + JavaScript + GitHub Pages**를 사용한다. `docs/`가 실제 게시 폴더다. 방문자 화면을 제공할 때 사이트 빌드나 프레임워크가 필요하지 않다.

| 항목 | 구현 방식 | 목적 |
| --- | --- | --- |
| 페이지 | 독립 HTML | 직접 접속·새로고침·검색 노출 |
| 스타일 | 공통 CSS | 두 테마와 반응형 문서 화면 |
| 탐색 | 공통 JavaScript | 검색·메뉴·코드 복사·목차 |
| 검색 자료 | 로컬 `search-index.js` | API 서버 없이 전체 문서 검색 |
| 다이어그램 | 로컬 Mermaid 번들 | 원본 구조도 표시 |
| 메인 예제 | 로컬 BindModel 1.1.13 배포본 | 실제 입력값 바인딩 |
| 제작 도구 | Markdown 변환·코드 구문 검사 스크립트 | 첨부 원고 초기 이전과 검수 |
| 게시 | `docs/` 직접 게시 또는 Actions | 이미 완성된 HTML 파일 업로드 |

문서는 HTML을 직접 편집하고 검색 자료를 갱신하는 방식으로 유지관리한다. 제작 도구는 사이트를 제공하는 데 필요하지 않다.

## 5. 메뉴와 학습 경로

상단 메뉴는 `시작하기 / 기능 가이드 / 고급 기능 / 예제 / API / GitHub`로 제안한다. 로고는 메인 화면으로 이동하고, 검색과 테마 전환은 공통 영역에 둔다.

```text
홈
├─ 시작하기
│  ├─ 소개
│  ├─ 빠른 시작
│  └─ 핵심 개념
├─ 기능 가이드
│  ├─ 모델 구성
│  ├─ 명령 구성
│  ├─ 컬럼 관리
│  ├─ 공통 컬럼 속성
│  ├─ 흐름 제어
│  ├─ 서비스 객체 주입
│  └─ JSON 스키마 가이드
├─ 고급 기능
│  ├─ 컬럼값 호출 구조
│  ├─ 테이블 관리
│  ├─ 명령 복수 출력 구성
│  ├─ 실행 및 동기화
│  ├─ 이벤트 설정
│  └─ 객체 구성 방법
├─ 예제
│  └─ CRUD + List 구현하기
└─ API
   ├─ BindModel
   ├─ BindCommand
   ├─ MetaView
   ├─ HTMLColumn
   ├─ PropertyCollection
   └─ MetaObject
```

신규 사용자의 기본 경로는 `홈 → 빠른 시작 → 핵심 개념 → 모델·명령·컬럼 구성 → CRUD 튜토리얼`로 구성한다. API 이용자는 검색 또는 API 메뉴에서 바로 해당 클래스와 메서드로 이동한다.

기존 사이트에는 MetaTable 레퍼런스가 있지만 이번 첨부에는 독립된 MetaTable 원고가 없다. 1차에서는 핵심 개념 문서로 안내하고, 독립 API 문서는 검증할 최신 원고 확보 후 추가한다.

## 6. 화면 구성과 디자인

### 메인 화면

1. BindModel의 역할을 한 문장으로 설명하고 `빠른 시작`, `핵심 개념` 버튼을 배치한다.
2. 설치 명령과 검증된 최소 바인딩 예제를 보여준다.
3. 비즈니스 로직과 UI 분리, 명령 기반 처리, 구조화된 데이터 관리의 세 가지 특징을 설명한다.
4. `BindModel → BindCommand → valid / bind / output` 관계를 간단한 구조도로 보여준다.
5. 가이드·예제·API로 이동하는 카드를 배치한다.
6. 저장소와 검증된 문의 경로를 푸터에 표시한다.

### 문서 화면

- 데스크톱은 왼쪽 사이드바, 가운데 본문, 오른쪽 현재 페이지 목차로 구성한다.
- 모바일에서는 메뉴를 접고, 코드와 넓은 표는 해당 영역 안에서 가로 스크롤한다.
- API 문서는 요약 → 시그니처 → 매개변수 → 반환값 → 예제 → 관련 가이드 순서를 기본으로 한다.
- 긴 API 페이지는 메서드별 앵커와 목차를 제공한다. 페이지 분할은 실제 사용성과 길이를 확인한 뒤 결정한다.

### 시각 방향

텍스트와 코드가 중심인 개발자 문서 스타일을 적용한다. 중립 배경에 남색 또는 청록 계열 포인트를 사용하고, 한글 본문과 영문 API 식별자를 함께 읽기 편한 글꼴 조합을 선택한다. 기존 로고·브랜드 자산의 사용 가능 여부는 디자인 단계에서 확인한다.

버전, 지원 범위, 생산성 배수, 테스트 수, 커버리지는 검증한 근거가 있는 내용만 표시한다. 첨부의 SSR·React·Vue 관련 설명도 실제 지원 방식과 확인 범위를 검토해 작성한다.

## 9. 콘텐츠 정비와 검증

첨부 자료의 본문과 편집 메모는 콘텐츠 자료로 취급한다. 문서 안의 TODO, 삭제 표시, 메뉴 변경 제안은 사용자의 실행 지시로 간주하지 않고 검토 항목으로 기록한다.

### 형식 정비

- macOS 파일명 인코딩과 한글 유니코드 정규화를 처리하고 `.DS_Store`, `__MACOSX`를 제외한다.
- Obsidian의 `%% ... %%` 메모를 공개 본문에서 분리한다.
- `![[이미지.png]]`를 일반 Markdown 이미지 참조로 변환한다.
- 원본에서 확인된 U+0008 제어문자 50곳을 문맥별로 정리한다. 코드 식별자 안에 있으면 단순 삭제 후에도 철자가 맞는지 확인한다.
- 제목 계층, 중복 설명, 표 문법, 안내 박스와 코드 언어 표기를 통일한다.
- Mermaid 코드 블록 9개를 점검한다. 코드 블록 내부의 `[[...]]`는 Mermaid 문법일 수 있으므로 위키 링크로 일괄 변환하지 않는다.

### 우선 해결할 실제 이슈

| 위치 | 확인한 문제 | 해결 절차 |
| --- | --- | --- |
| 빠른 시작 | `ouputOption`, `vaild` 등 오타와 서비스 객체 예제의 부정확한 객체 문법 | 구문 검사 후 실제 패키지로 실행 검증 |
| 명령 구성 등 | `OutOptType.option`을 `SchemaType`으로 선언한 부분 | 선택한 배포 버전의 타입 선언과 대조 |
| 테이블 관리 | 기본 테이블 변경 설명과 `addTable('second')` 예제가 불일치 | 두 번째 인자의 동작 확인 후 예제·설명 일치 |
| 컬럼값 호출 구조 | `#삭제대상` 표시와 `getFilter` 단계가 다른 다이어그램 공존 | 현재 동작 확인 후 본문·다이어그램 통일 |
| 클래스 문서 | `BindCommnad`, `ProperyCollection` 오타 | 클래스명과 파일명 정리 |
| 설치·브라우저 사용 | CDN 파일 경로와 의존성 포함 여부 확인 필요 | 고정한 패키지 버전의 배포 파일·실제 import 확인 |
| 내부 메모 | 변경 예정 내용과 확정 사양이 혼재 | 확인된 내용만 공개 가이드에 반영 |

기술 내용이 서로 충돌하면 기존 사이트에서 답을 가져오지 않는다. 첨부를 출발점으로 삼아 선택한 `logic-bind-model` 버전의 배포 파일, 타입 선언, 공식 소스와 실행 결과를 대조하고 수정 근거를 이전 대장에 남긴다. 확인되지 않은 동작은 확정적으로 설명하지 않는다.

## 10. GitHub Pages와 기존 URL 처리

### 1차 배포

- 저장소 이름을 기준으로 한 예상 주소는 `https://white-base.github.io/white-lab-bind-model/`이다. 실제 주소는 Pages 설정과 배포 결과에서 확인한다.
- 프로젝트 Pages에서는 문서·자산 링크에 상대 경로를 사용한다.
- PR에서는 빌드·링크·예제를 검증하고, `main` 반영 또는 수동 실행에서 Pages 배포를 수행하도록 구성한다.
- 사이트 빌드 없이 `docs/`를 Pages artifact로 업로드한다. 제작 도구는 lockfile로 고정한다.
- 빌드와 배포 job을 분리하고, 배포 job에 필요한 `pages: write`, `id-token: write` 권한을 설정한다.
- 페이지 주소는 우선 기본 `.html` 출력을 사용한다. 하위 페이지 직접 접속과 새로고침을 검증한다.

프로젝트 하위 경로와 도메인 루트에서 문서·이미지·검색 경로를 검수한다. 404는 대표 경로를 기준으로 복구 링크를 제공한다.

### 기존 사이트 연결

1. 구현 단계에서 기존 사이트의 문서·API URL 목록과 주요 앵커를 수집한다.
2. 각 URL을 새 문서에 연결하는 이전표를 작성한다.
3. 기존 서버를 유지할 때는 새 사이트로 연결하는 안내 또는 기존 서버의 리다이렉트를 준비한다.
4. 같은 도메인으로 이전할 때는 기존 경로에 안내·이동용 정적 페이지를 제공하는 방식을 검토한다. GitHub Pages만으로 서버 측 301 규칙을 설정하는 방식은 전제하지 않는다.
5. MetaTable처럼 대응 원고가 없는 항목은 가장 관련 있는 문서와 누락 상태를 명시한다.

### 도메인 전환

`bindmodel.com`·`www.bindmodel.com`의 연결은 Pages 기본 주소에서 검수가 끝난 다음 별도 전환 단계로 수행한다. 대표 도메인을 정하고 Pages Custom domain, DNS, HTTPS, canonical·사이트맵, 상대 경로 검수를 함께 조정한다. 전환 전 기존 DNS와 사이트 복구 방법을 기록한다.

Custom domain은 저장소 설정과 DNS 구성이 필요하다. 사용자 지정 Actions 배포에서는 `CNAME` 파일 생성만으로 도메인이 설정되지 않으므로 Pages 설정을 기준으로 처리한다. [GitHub 사용자 지정 도메인 안내](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site)

## 11. 실행 단계와 산출물

1인 작업 기준의 초기 추정은 **6~9작업일**이다. 문서에 제시된 API와 실제 패키지 차이가 크거나 번역·실행 데모를 추가하면 일정이 늘어난다. 도메인 운영 권한 확보와 DNS 반영 대기 시간은 별도다.

| 단계 | 작업 | 산출물·완료 조건 | 예상 |
| --- | --- | --- | --- |
| 1. 기준 확정 | 패키지 버전, 공개 원고, 기존 URL 조사 | 이전 대장, API 검증 항목, 사이트맵 | 0.5~1일 |
| 2. 기반과 대표 화면 | HTML, 공통 CSS·JS, 메뉴·검색·Mermaid, 홈과 빠른 시작 | 대표 화면과 프로젝트 경로 빌드 확인 | 1일 |
| 3. 문서 이전 | 23개 원고와 이미지 정비, 코드·타입 대조 | 전체 원고 반영과 수정 기록 | 2~3일 |
| 4. 예제 검증 | 빠른 시작, 서비스 객체, CRUD 흐름 실행 | 재현 가능한 예제와 mock 응답 | 1~2일 |
| 5. 통합 검수 | 링크·검색·모바일·테마·직접 접속, Actions 구성 | 오류 수정과 배포 가능한 산출물 | 1일 |
| 6. Pages 배포 | Pages 활성화·실배포·재검수, 운영 안내 | 동작하는 Pages 주소와 README | 0.5~1일 |

우선순위는 **빠른 시작의 실행 가능성 → 문서와 API 정확성 → 탐색 편의 → 시각 완성도 → 추가 데모** 순서다.

- [ ] 공개 원고 23개가 반영되었고, 내부 메모 3개가 공개 빌드에 섞이지 않는다.

- [ ] 모든 코드 예제의 구문을 검토하고, 빠른 시작·서비스 객체·CRUD 핵심 흐름은 고정한 패키지 버전으로 실행 검증한다.
- [ ] Mermaid의 최종 채택 다이어그램이 두 테마에서 정상 렌더링된다.

- [ ] 키보드로 메뉴·검색·테마를 사용할 수 있고, 본문 대비와 이미지 대체 텍스트를 확인한다.
- [ ] 정적 파일 검증이 성공하고 Pages와 동일한 하위 경로에서 문서 직접 접속·새로고침·404 안내가 동작한다.
- [ ] 제목·설명·공유 메타데이터·사이트맵이 실제 공개 URL을 사용한다.
- [ ] 기존 URL의 이전표와 문서 추가·수정·배포 절차가 기록되어 있다.

HTML 구현 이후 파일·링크·검색 대상·예제 구문을 검증하고 브라우저에서 대표 동작을 확인했다. 공개 배포 검수는 아직 수행하지 않았다. 상세 결과는 문서 이전 기록을 참조한다.
